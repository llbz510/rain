## 1. 本文件回答什么

本文件只回答一个问题：**当有人声称某条已确认的视觉规范已经落地时，用什么数字、什么证据、由谁来判断真假。**

它回答不了、也不回答的问题：

- 某条 AC 是否已完成（由 AC 状态与 `harness-coverage.md` 回答）；
- 视觉 Evidence 是否已签发（由对应 AC 的 Required Evidence tier 与真实证据包回答）；
- 用户是否还需要做产品取舍（取舍只能由用户决定，AI 只能列选项）。

## 2. 视觉审查员（visual reviewer）

### 2.1 角色

视觉审查员是一个**独立于实现者**的只读裁判。它可以是人，也可以是另一个上下文隔离的 AI 代理，但**不能是写出被审代码/被审文档的那一方**。

### 2.2 输入（缺一不可）

审查员只能基于以下输入作判断：

1. **目标提交**（精确 commit SHA）上的生产应用，运行在**真实桌面宿主**（Tauri + 真实 WebView2），或由托管 Windows 上的桌面 workflow 产出的一次真实运行。
2. **截图**：目标提交、目标视口下的真实渲染截图（附件形态）。
3. **DOM 几何与颜色实测**：同一次运行、同一视口下从**运行中的应用**读出的选择器、`getBoundingClientRect()` 几何、`getComputedStyle()` 字体/行高/边框/圆角/背景、逐层合成的实际颜色与按 §3.2 算出的对比度。
4. **本合同的具体条目编号**（`VC-01`…`VC-19`；其中 `VC-18` 是保留空号，编号与 AC 的对照见 §4.2、该空号的原因见 §4.3）。

### 2.3 输出（结构化）

审查员必须逐条给出：

- `VC-xx`：判据编号；
- `verdict`：`pass` / `needs_revision`，**只能由实测数字决定**；
- `measured`：实测值（数字 + 单位 + 采样视口 + 选择器）；
- `threshold`：本合同要求的阈值与允许误差；
- `evidence`：截图附件名 + 实测数据的存放位置（或复制进报告的相关行）；
- 判 `needs_revision` 时给出 `requiredFix`（改哪个值、改到多少才算过）。

### 2.4 三条铁律

1. **截图好看 ≠ 合规。** 视觉观感不是判据；没有实测数字的截图**不构成任何一条 `VC-xx` 的证据**。
2. **没有 DOM 几何与颜色实测的截图，不构成 Visual Evidence。** 它只能作为附件。
3. **审查员不回原始数据就不得下结论。** 被引用的每一个数字都必须能由审查员自己从目标提交重新读出。

### 2.5 审查员不得做的事

- 不得用「看起来统一」「感觉符合暗色主题」这类判断代替数字；
- 不得把 token 存在（CSS 变量或常量存在）当作「被使用」；
- 不得用 jsdom 或任何非真实渲染环境的结果代替真实桌面实测；
- 不得替用户决定颜色怎么改、是否分两套值、状态冲突谁优先（见 §6）；
- 不得宣布任何 AC 完成或等级变化。

## 3. 裁判规则

### 3.1 每条判据的构成

每条 `VC-xx` 必须能回答四个问题：**在哪个页面/组件上**、**判什么数字**、**允许多少误差**、**要什么证据形态**。缺任一项的条目不得进入裁判。

### 3.2 测量协议

- **颜色**：以运行中的应用实际合成后的颜色为准（`rgba` 需按层合成到不透明底色上再比较），十六进制按 sRGB 通道比较。
- **对比度**：按 WCAG 2.1 相对亮度公式 `(L1 + 0.05) / (L2 + 0.05)` 计算；文本按 4.5:1（普通文本）或 3:1（大号文本，即 ≥18.66px 粗体或 ≥24px），非文本（边框、进度条、状态指示等 UI 组件与图形）按 3:1。
- **几何**：`getBoundingClientRect()` 的 CSS 逻辑像素；受 DPI 缩放影响的渲染像素按视口 `devicePixelRatio` 换算回逻辑像素后比较。
- **字体/行高/字重/时长**：读 `getComputedStyle()`；时长同时核对真实动画/过渡的实际耗时。
- **视口**：桌面窗口默认尺寸，以及本合同明确要求的窄/宽视口（见 `VC-11`）。

### 3.3 允许误差

| 测量类型 | 允许误差 |
| --- | --- |
| 颜色值（**不论是否已确认**，同一运行内的同值判定） | 每个 RGB 通道 ±1 |
| 对比度比值 | ±0.05 |
| 由 CSS 令牌直接推出的几何（如间距、圆角、固定高度） | ±0.5 逻辑像素 |
| 依赖布局/字体度量的已渲染几何（如文本行数、网格列数、进度条高度） | ±2 逻辑像素 |
| 字号、字重、行高、圆角档位、间距档位 | 精确相等，不许近似 |
| 动效时长（含 reduced-motion 下的即时化） | ±10ms |
| 比例（如缩略图 16:9） | 按 §4 该条给出的像素容差反算 |

**容差与「确认」是两件事**：容差只规定「同一个目标值允许测出多少偏差」，它**不把任何未量化的值变成已确认的值**。

### 3.3.1 数值化参数（`✱`）：测量形态已定，取值本身尚未被 M13 量化

M13 有几处只给出**定性描述或范围**，没有精确数字。本合同必须让它们可测，因此统一处理为：**把已确认的定性/范围写成「取值必须落在给定边界内」，并把该条的取值列为待确认的数值化参数（标记 `✱`）**。`✱` 不是新语义，也不放宽任何已确认要求；它表示「具体取值需由用户确认或由后续视觉审查员复核」。

| 参数 | M13 原文 | 本合同的可测边界 |
| --- | --- | --- |
| 白 `#ffffff` | 决策 70「文字 = 白色」、决策 78「白」 | 白端按 sRGB `#ffffff` 裁判；`VC-02` 的文字两档（`#e5e5e5` / `#8a8a8a`）是另一个已量化维度，两者分别成立 |
| 类型色极淡底 alpha | 决策 70「极淡底」、决策 71「淡底」 | `0.05 ≤ alpha ≤ 0.20`，同一载体全应用一致；具体值标 `✱` |
| 主按钮「描边款」 | 决策 65「主按钮 = 描边款」 | 底色 = 背景色或面板色（不得为彩色实底）、边框 ≥1px 且取自中性色阶、不得使用 `#4a9eff`；具体边框宽度与颜色标 `✱` |
| 「模式/Tab 激活态 = 底色变暗」 | 决策 65 | 激活底色的相对亮度**严格低于**未激活底色；变暗幅度标 `✱` |

| 卡片圆角 | 决策 77 未规定（072 已由 077 接管，不再作为依据） | 必须取自冻结圆角阶梯 `0/4/8/12/胶囊`；具体档位标 `✱`（未取阶梯值即违反 `VC-15`） |
| 「文本区类型胶囊」形态 | 决策 71 | 类型色字 + 同色淡底 + 同色细边（≥1px）；具体内边距标 `✱` |
| 「浅灰白 2px 虚线」聚焦圈 | 决策 65 | 宽度 `2px`、`border-style: dashed`、颜色取自中性色阶浅端；具体色值标 `✱` |
| 状态色具体色值 | 决策 69 只给「红 / 黄 / 灰」 | 必须落在 §5.2 已验算且达标的集合内（红取 `#dc2626` 或 `#f85149`、黄取 `#f59e0b`、灰取 `#8a8a8a`），色相不得越出红/黄/灰 |
| 就绪卡进度条中性色 | 决策 72「中性白/浅灰」（该决策已 `Out-of-scope`，决策 77 未接管其颜色） | 必须是**中性色**（不得使用类型色、不得使用强调色）；具体色值标 `✱` |

**§5.2 的对比度是对目标提交 `9639410c` 上 `src/index.css` 与 `src/ui/components/settings/shared.ts` 里已落库的当前值的实测。** 若后续任何 Slice 调整了这些色值，`VCGAP-09`…`VCGAP-19` 中依赖色值的复测数字（`09`…`15`、`17`）必须重算；「修到哪个值」由 `VCQ-01`/`VCQ-02` 决定，本合同不预先写死新色值。

**`✱` 参数的用途**：它们让「尚未量化的已确认要求」变成可测边界，**不改变**该要求本身；任何一个 `✱` 参数被用户定值后，本合同只做替换式更新并把该条从 `✱` 移出。

### 3.4 证据形态（统一格式）

一次视觉证据包必须包含，并与目标提交 SHA 绑定：

1. 目标提交 SHA、视口尺寸（含 `devicePixelRatio`）、宿主与版本；
2. 截图（附件）；
3. 每个判据的实测记录：`VC-xx` + 选择器 + 几何 + 计算样式 + 实际合成颜色 + 对比度比值 + 采样视口；
4. 逐条 `pass` / `needs_revision` 结论与差值。

**截图单独存在时，本合同的任何一条都判不了。**

**部分覆盖也合法，但必须诚实标注**：证据包允许只覆盖一部分 `VC-xx`；此时必须显式列出「本次已测」与「本次未测」两张清单，并对已测项逐条给出 `pass`/`needs_revision`。**未测项一律视为未取得证据**，不得用「其余看起来一致」推断通过。

### 3.5 明确不构成裁判（不得被写成判据，也不得用来支撑结论）

以下条目在 M13 中属于观感/相对描述，**不构成本合同的裁判项**：

- 整体观感（「沉稳」「干净」「专业」）与截图美观度；
- 「主背景近黑略带蓝」「面板深灰」「分隔线极淡灰」「文字白·浅灰两级」这类**相对描述**（只作为选择具体色值时的意图说明，裁判一律用具体色值与对比度）；
- 视觉平衡、留白是否「舒服」、层次是否「清爽」；
- 中英文搭配是否「同族感」（只能裁判字体族声明与字号/行高，不能裁判观感）；
- 圆角/间距的「节奏感」（只能裁判是否取自冻结阶梯）；
- 状态是否「一眼可辨」（只能裁判对比度、是否纯颜色、是否有文字与形状冗余）；
- 滚动条外观、操作系统窗口动画、视频画面本身。

## 6. 待用户决策的三项（AI 不得代替用户决定）

以下三项**必须由用户选择**。AI 只列选项与影响，不得静默采用其中任何一项。三项都还没有答案，因此 §5.3 第一桶的 12 条（`VCGAP-01`、`03`、`04`、`05`、`09`…`15`、`17`）暂时**不能**进入修复；第二桶的 7 条不受影响。

### `VCQ-01` 对比度不达标的颜色怎么修？

背景：`VCGAP-09`…`VCGAP-15` 与 `VCGAP-17` 共 **8 处**对比度不达标（`VCGAP-16` 是几何项、`VCGAP-19` 是依据项，均不在对比度范围；`VCGAP-14`/`VCGAP-15` 是前瞻项：类型色当前零使用，见 `VCGAP-03`）。其中「1px 边框 1.53:1」有两种完全不同的解法：把边框调亮到 3:1，或者**不再让边框承担可辨识职责**（改为底色块分层 / 加内阴影 / 加粗重点控件边框）。M13 决策 64 里「分隔线 = 极淡灰」是已确认意图，但**没有**给出「控件边框也必须 3:1」的结论——这属于新判断，必须由用户定。

- **A（只调数值）**：保持现有版式与决策 65 的「无品牌强调色」写法，只把有问题的色值调到达标（例如把主按钮改成中性色描边款，白字压蓝底的问题随之消失）。
- **B（改样式）**：把出问题的元素改成描边款 / 加中性底，不主要靠改色值（更贴近决策 65，但改动面更大）。
- **C（两者都做）**：主按钮改描边款（消掉 2.75:1），其余只调色值。
- **附加子问题（AA 适用面）**：只要求「正文 + 主操作」达标，还是**连 1px 边框、状态色徽章、类型色文字都一律达标**？（后者会连带改动更多已确认的观感取值。）

### `VCQ-02` 类型色 / 状态色是否按底色分两套值？

背景：`VCGAP-04` 发现实现里已经存在两套颜色（M13 一套、设置页一套）。一套值打到所有表面时，部分组合达不到 4.5:1（`VCGAP-14`、`VCGAP-15`）；而设置页那一套压面板**全部达标**（`#539bf5` 6.07:1、`#3fb950` 6.81:1、`#db6d28` 5.13:1）。按底色分两套则两套都能达标，但「全界面唯一颜色映射」（决策 66）需要重新解释。

- **A（一套值）**：全局只保留一套类型色/状态色，必要时调整色值使它在所有底色上达标（最贴近决策 66 的字面）。
- **B（两套值）**：按底色分两套（深底一套、面板底一套），并明确「同一类型在不同底色上允许不同色值」这一解释。
- **C（一套值 + 调透明度）**：色值只保留一套，靠调整淡底透明度让彩字达标。

### `VCQ-03` 两种状态冲突时谁优先？

背景：决策 69（状态色：失败红/处理中黄/排队灰）与决策 67/68（选中 = 变暗、播放 = 变亮）可能同时作用于同一元素（例如一个失败或处理中的卡片同时被选中，或目录里某个节点同时是「当前播放」且是「处理中」）。M13 没有写明优先级。

- **A（状态色最优先）**：状态（失败/处理中/排队）优先，选中与播放让位（或改为只保留非颜色信号）。
- **B（选中 / 播放最优先）**：选中与播放优先，状态改为只靠徽章/文字表达。
- **C（允许叠加）**：允许三者同时呈现，但必须满足：底色仍满足变暗/变亮的方向要求，且所有文字仍达标。
